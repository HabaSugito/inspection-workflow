## Summary

An operations user creates an inspection from the page, without calling the API by hand. The detail of an inspection, and the control for its next step, are visible without the user having to discover how to open them.

## Why this spec exists

A reviewer ran the submission and reported: "I only see a list … there's no form or feature to add customer info and send the inspection details to the customer or start new inspections."

| What the reviewer expected | What the submission did | What this spec does |
|---|---|---|
| A form to add an inspection | Creating was possible through the API only. DS-001 left the form out because no story asked for it | Adds the form. See US-401 and US-402 |
| To see more than a list, and to start an inspection | The detail panel and the next-step control existed, but opened only when the registration text in a row was clicked. Nothing on the page said so | Makes them visible without a discovery step. See US-403 and US-404 |
| To send the inspection details to the customer | Not built | Not built. The brief puts notifications out of scope. See "Out of scope" |

The second row is a defect in the first submission: the brief asks for "a simple way to view an inspection and trigger its next valid transition", and a way that the reviewer did not find was not simple.

## User stories

| ID | Story |
|---|---|
| US-401 | As an operations user, I can create an inspection from the page by entering the customer name, vehicle registration, requested date and optional notes, so that I do not need another tool. |
| US-402 | As an operations user, I see which field is wrong and why when my input is refused, and what I typed is kept, so that I can correct it. |
| US-403 | As an operations user, I see the detail of an inspection and the control for its next step as soon as the page has loaded, so that I do not have to find out how to open them. |
| US-404 | As an operations user, I can select an inspection by clicking anywhere on its row, or with a labelled button, so that selecting is obvious with a mouse and possible with a keyboard. |

## Screen

The page keeps its two panels.

- **Left panel.** A "New inspection" button above the list. Each row shows the status, the vehicle registration and the customer name, and ends with a "View" button. The whole row can be clicked.
- **Right panel.** It shows one of two things: the detail of the selected inspection, as today, or the form for a new inspection.

When the page has loaded and there is at least one inspection, the newest one is selected, so the right panel shows a detail and a next-step control from the start.

The form has four fields: customer name, vehicle registration, requested date and notes. It has a "Create inspection" button and a "Cancel" button.

## Acceptance criteria

All criteria are for the UI and are checked by hand in a browser, unless the technical spec says otherwise.

| ID | Story | Criterion |
|---|---|---|
| UI-401 | US-401 | The page has a "New inspection" button. Using it shows a form with the four fields in the right panel. |
| UI-402 | US-401 | Submitting valid input creates the inspection. The form closes, the new inspection is at the top of the list, it is selected, and its detail shows status `pending` and the control to assign an inspector. |
| UI-403 | US-401 | The inspection created from the page is the same as one created through the API: the registration is shown in upper case, and notes left empty show as "—". |
| UI-404 | US-402 | When the server refuses the input, each message is shown next to the field it belongs to, and the values typed are kept. Nothing is added to the list. |
| UI-405 | US-402 | When the request fails for another reason, such as the server being unreachable, one message is shown in the form, and the values typed are kept. |
| UI-406 | US-401 | "Cancel" closes the form without creating anything and shows the inspection that was selected before. |
| UI-407 | US-401 | While the request is in flight, the "Create inspection" button cannot be used again, so one click cannot create two inspections. |
| UI-408 | US-403 | After the page has loaded with at least one inspection, the newest is selected and the right panel shows its detail and next-step control. With no inspections, the right panel invites the user to create one. |
| UI-409 | US-404 | Clicking anywhere on a row selects that inspection. |
| UI-410 | US-404 | Each row has a "View" button that selects it, reachable with the Tab key and usable with Enter or Space. The selected row is marked. |

## Out of scope

From the brief: authentication, payments, photo uploads, notifications, deployment.

**Sending the inspection details to the customer is a notification, so it is not built.** The README says how it would be approached in production.

Not in any story, so not built: editing or deleting an inspection, searching or filtering the list, and creating an inspector record.

No change to the API. `POST /api/inspections` already exists and is covered by DS-001.

## Assumptions

| ID | Assumption |
|---|---|
| A-401 | The page is used by an operations user. The customer does not use it. The customer's request reaches the operations user by another route, such as a phone call, and the operations user enters it. |
| A-402 | The rules for the four fields stay on the server (DS-001). The page does not check them before sending. It shows what the server answers. |
| A-403 | "Start new inspections" in the reviewer's message means creating an inspection. Starting an assigned inspection, `assigned` → `in_progress`, already exists (DS-003 UI-302). |

## Decisions

These points are not settled by the brief or by the reviewer's message. The author decided them before the technical spec was built.

| ID | Question | Outcome | Status |
|---|---|---|---|
| OQ-401 | Should the newest inspection be selected when the page loads? | Decided: yes. It is the most direct fix for "I only see a list": the detail and the next-step control are on screen without any click | Decided |
| OQ-402 | Where does the form appear? | Decided: in the right panel, in place of the detail. The page keeps two panels and needs no dialog or second page | Decided |
| OQ-403 | Should the page check the input before sending, for example mark fields as required or block past dates in the date picker? | Decided: no. `docs/architecture.md` says the rules live on the server and the page does not repeat them. The form shows the server's messages per field | Decided |
| OQ-404 | Should this spec add automated tests for the UI? | Decided: not in this spec. It would add test dependencies, and the README lists UI tests as the first improvement. If wanted, it becomes its own technical spec so that the dependency is reviewed on its own | Decided |
