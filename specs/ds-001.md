This document says what is built, not how. The user stories are the source of truth: anything not traceable to a story is out of scope.

## Summary

An API client records a customer's request for a pre-purchase vehicle inspection. Invalid input is refused with an error that names the failing fields.

## User stories

| ID | Story |
|---|---|
| US-101 | As an API client, I can create an inspection with a customer name, vehicle registration and requested date, so that the customer's request is recorded. |
| US-102 | As an API client, I can add notes to the request or leave them out. |
| US-103 | As an API client, I get an error naming the failing fields when I send invalid data, so that I can correct the request. |

## Information held for an inspection

| Item | Required | Rule |
|---|---|---|
| Customer name | Yes | Text, up to 255 characters |
| Vehicle registration | Yes | Text, up to 20 characters. Stored in upper case |
| Requested date | Yes | A date, written `YYYY-MM-DD`, today or later |
| Notes | No | Text, up to 2000 characters |
| Status | Set by the system | Always `pending` when created |
| Inspector name | Set by the system | Always empty when created |

## Acceptance criteria

| ID | Story | Criterion |
|---|---|---|
| AC-101 | US-101 | A valid request returns 201 and the created inspection, in status `pending` with no inspector. |
| AC-102 | US-102 | Notes may be omitted. The inspection is created with empty notes. |
| AC-103 | US-103 | A missing customer name, vehicle registration or requested date returns 422 with an error for that field. |
| AC-104 | US-103 | A requested date that is not a valid date returns 422 with an error for that field. |
| AC-105 | US-103 | A value longer than its limit returns 422 with an error for that field. |
| AC-106 | US-103 | A 422 response is JSON with a `message` and the errors listed per field. Nothing is stored. |
| AC-107 | US-101 | A status or inspector name sent in the request is ignored. |
| AC-108 | US-103 | A requested date before today returns 422 with an error for that field. Today's date is accepted. |
| AC-109 | US-101 | The vehicle registration is stored and returned in upper case, whatever case was sent. |

## Out of scope

From the brief: authentication, payments, photo uploads, notifications, deployment.

Not in any story, so not built: editing or deleting an inspection, and a create form in the UI.

## Assumptions

| ID | Assumption |
|---|---|
| A-101 | There is no authentication, so any caller may create an inspection. |
| A-102 | Vehicle registration is free text. No country-specific format is enforced, and spaces inside it are kept as sent. |
| A-103 | Sending the same request twice creates two inspections. |
| A-104 | "Today" is the current date on the server. |

## Decisions

These points are not settled by the brief. The author decided them one at a time.

| ID | Question | Outcome |
|---|---|---|
| OQ-101 | Should the requested date be rejected when it is in the past? | Decided: yes. An inspection is requested for a future visit, so a past date is treated as an input mistake. See AC-108 |
| OQ-102 | Should the vehicle registration be upper-cased when stored? | Decided: yes. The same registration then reads the same in the list however it was typed. See AC-109 |
